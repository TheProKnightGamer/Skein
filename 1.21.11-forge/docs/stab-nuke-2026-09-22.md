# Size-1 Stab Nuke — 2026-09-22

The latest local Orbital build tested was **7.0-stab-nuke.3**, from the
`orbital-stab-nuke/dist` directory. The test invokes `orbital:stab_nuke_1` from
the actual mod jar. It queues 631 measured impact points, each spawning 62 TNT:
**39,122 TNT total**. Its original queue releases 128 stabs per tick, so the
strike produces four batches of 7,936 TNT and a final batch of 7,378.

The strike completes without a crash or lost detonations, but causes long
server stalls. The changes below reduce the cost; they do not bring this
workload close to Minecraft's 50 ms tick budget.

## Performance results

Two unprofiled runs per packaged build, with one server running at a time:

| Measurement | Before | Optimized |
| --- | ---: | ---: |
| Mean total of the five explosion ticks | 64.602 s | 49.950 s |
| Worst tick observed | 15.870 s | 12.626 s |
| TNT detonated per run | 39,122 | 39,122 |

The total explosion-tick time fell **22.7%**, saving about 14.65 seconds per
strike in these runs. Before totals were 65.359 and 63.845 seconds; optimized
totals were 51.312 and 48.589 seconds. Initial marker placement took 30–35 ms.
The original queue still took exactly five explosion ticks; the optimization
does not spread explosions across additional ticks.

[Per-tick CSV](stab-nuke-2026-09-22.csv). The compared directories are `baseline`,
`baseline-2`, `final-1`, and `final-2` under `build/stab-nuke`. Development and
profile runs are retained separately and excluded from these averages. There
were no concurrent builds or other test servers during the measurements. Two
local runs per build establish the observed improvement, not a universal timing
guarantee. The total above excludes quiet recovery ticks and initial marker setup.

## Test conditions

- Minecraft 1.21.1, NeoForge 21.1.219, Java 21, Core i7-14700K.
- Updated SuperChunk 0.4.0 with bundled Lithium, SpeeDeeEntity 1.0.2.
- Skein's all-CPU option enabled: 27 workers, adaptive scheduling, `RETHROW`.
- CPU chunk generation with four SuperChunk workers, 4 GiB Java heap.
- Fresh superflat world, seed 12345, with bedrock, 123 stone layers, three dirt
  layers and grass. Surface Y=64; the lower stab charges have real stone to hit.
- Launch at (2080.5, 64, 32.5), 1,089 chunks preloaded, structures and mob
  spawning disabled. Block drops remain enabled.
- Sixty warmup ticks. Tick measurements include the mod's queued summon commands
  and the real explosions. Initial marker placement is timed separately.
- No explosion cancellation, TNT removal shortcut, changed batch size, reduced
  blast radius, altered fuse, or increased watchdog limit.

Every run verifies 631 starting markers, exactly 39,122 tagged TNT spawns,
exactly one explosion event per TNT, an empty queue, no remaining strike TNT,
zero tick failures, and no quarantined dimension. Final runs also observe 20
quiet recovery ticks and save normally on shutdown. These are disposable
dedicated servers; this does not measure client rendering or the full client
mod collection.

## Changes

1. **Skip repeated affected-block insertions.** A per-explosion 512-byte bitset
   remembers positions already added within a 16-block cube. Larger blasts use
   the original set outside that cube. All ray steps, resistance callbacks and
   block-veto callbacks still run. First insertions reach the existing set in
   the same order, preserving its iteration order relative to the prior Skein
   build. This is not a cache of block states or explosion resistance.
2. **Reuse the private chunk cache for the exclusive level owner.** Dense
   sequential entity work can use Skein's existing chunk cache as well as cell
   workers. Misses still take the original chunk-fetch path. Cache entries are
   scoped to the chunk source and invalidated by vanilla's cache-clear
   generation; chunks currently being loaded are not remembered by the new path.
3. **Recognize newly created short-fuse TNT.** Setting a fuse to one or less
   requests the same one-shot scheduling probe as the existing countdown hint.
   Previously, TNT created with fuse 1 never passed through the fuse-2 hook.
   Eligibility checks and spatial isolation still apply. This does not create
   parallel work for the compact size-1 pattern by itself.

JFR sampling identified repeated affected-block insertion, chunk lookup and
exposure ray traversal as hot paths. A different coordinate hash was also
measured and discarded because it did not improve the full strike. Profiled
runs are excluded from the performance comparison.

The compact TNT pattern exposes no independent entity cells to Skein's current
scheduler: the benchmark records zero parallel entity work and about one busy
core across the measured tick threads. Increasing worker count cannot fix that.
Interacting explosions must observe prior terrain changes and knockback;
running them concurrently without preserving those dependencies would change
the strike.

## Correctness

The optimized build passed the core geometry, precedence, component-order and
nested-barrier checks. Real server verification passed:

- 32 seeded vanilla/optimized explosion comparisons: affected block sets,
  callback traces, remaining random state, damage and knockback; including
  water, waterlogged blocks, world boundaries and direct chunk mutations.
- Serial-owner cache hits, invalidation through vanilla `clearCache`, and
  isolation between chunk sources.
- Normal countdown and newly created short-fuse scheduling hints, one-shot
  expiry, unchanged fuse values, and phase-eligibility vetoes.
- Projectile query comparisons and SpeeDeeEntity's 512 moving entities over
  100 ticks, split between the cluster and grid schedulers.
- All four SuperChunk parallel phases, 288 hopper/chest pairs with exact item
  conservation, 96 decayed leaves, 192 scheduled leaf updates, four concurrent
  cold chunk loads, and config reload.

The full checks passed with bundled Lithium and standalone Lithium 0.15.4.
One initial standalone run reached the original 100-tick cutoff with a leaf
still present. At random-tick speed 256, individual leaves can legitimately
outlast that window. The fixture now continues its entity stress until the
leaves finish, up to a firm 400-tick limit, and then enforces the same decay
assertions. The rerun passed. No gameplay random-tick behavior was changed.
The passing standalone run also logged two `Unprimed heightmap:
WORLD_SURFACE_WG` messages during world preparation, a diagnostic previously
observed with the original SuperChunk build; it is not a wholly clean-log run.

The final packaged jar also retained all 2,000 snowballs in the bubble-column
regression test, with each ticking exactly 600 times. Across 400 measured ticks
after 200 warmup ticks, mean tick time was **2.362 ms**, median **2.245 ms**, and
p95 **2.724 ms**. The recorded position/velocity trace matched all 400 samples
from the preceding build. This mean lies within the preceding two-run range
of 2.186–2.469 ms; this single regression run does not establish a new speedup.

Affected-block set equality is not proof of complete post-explosion world
equivalence. The pre-existing open-addressed set already differs in iteration
order from vanilla's hash set. This change preserves the prior Skein set's
first-insertion and iteration order.

## Reproduction and artifacts

The opt-in `StabBenchmark` fixture is excluded from the gameplay jar. Supply the
latest local Orbital jar, SpeeDeeEntity jar, and a directory containing the
updated SuperChunk jar:

```sh
./gradlew runSpeedeeTest --offline --console=plain \
  -PstabBenchmark \
  -PspeedeeTestJar=/path/to/speedeeentity.jar \
  -PorbitalTestJar=/path/to/Orbital-Strike-Cannon-V7-Stab-Nuke-1.21.1.jar \
  -PextraTestModsDir=/path/to/superchunk-only-mods \
  -PtestConfigDir=build/superchunk-parallel/benchmark-config \
  -PtestDirectory=build/stab-nuke/reproduction \
  -PbenchmarkSkeinJar=build/libs/skein-1.0.0.jar
```

Use a fresh test directory. The config directory used here sets all CPU threads,
adaptive scheduling and `RETHROW`, and disables SuperChunk's GPU world generation.
Add `-PcinematicProfile` only for a separate JFR diagnostic run.
Raw tick CSVs, results and logs are under `build/stab-nuke/`.
